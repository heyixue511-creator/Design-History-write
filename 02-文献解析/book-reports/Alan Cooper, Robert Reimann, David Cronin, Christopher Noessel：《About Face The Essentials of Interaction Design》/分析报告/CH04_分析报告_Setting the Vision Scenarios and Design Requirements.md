# CH 04 分析报告：Setting the Vision: Scenarios and Design Requirements（设定愿景：场景与设计需求）

---

### 一、章节概述

本章解决了 Goal-Directed Design 流程中最关键的一步：如何从"我们了解了用户"过渡到"我们知道该设计什么"。Cooper 团队提出了以叙事为中心的需求定义方法——通过情境场景（Context Scenario）描述理想用户体验，然后从场景中提取设计需求。本章区分了三种场景类型（情境场景、关键路径场景、验证场景），清晰界定了"设计需求"与"功能列表"和"产品规格"的本质区别，并提供了从创建问题声明到提取数据/功能/情境需求的完整操作流程。

---

### 二、核心概念与术语

| 术语 | 英文 | 定义 |
|------|------|------|
| 情境场景 | Context Scenario | 描述理想用户体验的高层叙事，不涉及具体界面 |
| 关键路径场景 | Key Path Scenario | 描述主要交互路径的界面层叙事 |
| 验证场景 | Validation Scenario | 测试设计对边缘情况适应性的压力场景 |
| 假装它是魔法 | Pretending It's Magic | 在场景中先忽略技术约束，聚焦理想体验的设计技术 |
| 设计需求 | Design Requirement | 用户为达成目标所需的信息和能力（非功能、非规格） |
| 问题声明 | Problem Statement | 对当前问题和机会的精炼陈述 |
| 愿景声明 | Vision Statement | 对设计目标的高层描述 |
| 用例 | Use Case | 系统与用户交互的技术描述（与场景的区别） |
| 用户故事 | User Story | 敏捷开发中的简短需求描述（与场景的区别） |
| 数据需求 | Data Requirement | 系统中必须呈现的对象和信息 |
| 功能需求 | Functional Requirement | 用户需要在系统对象上执行的操作 |
| 情境需求 | Contextual Requirement | 系统对象之间的依赖和显示关系 |

### 三、关键论点与分析

**论点 1：叙事（Narrative）是最有力的设计工具**

Cooper 引用了 Brenda Laurel 关于叙事的观点，论证讲故事是人类最古老和最有效的沟通方式。相比于功能列表或 UML 图，一个关于具体 Persona 如何达成具体目标的生动故事更容易让整个团队建立共识。场景使抽象的需求变得可感知。

**论点 2：场景 vs 用例 vs 用户故事**

这是本章最有方法论价值的区分：

| 维度 | 场景（Scenario） | 用例（Use Case） | 用户故事（User Story） |
|------|-----------------|-----------------|---------------------|
| 视角 | 用户的行为和动机 | 系统的功能行为 | 用户想要的简短描述 |
| 格式 | 叙事（narrative） | 技术规格（spec） | 一句话模板 |
| 目的 | 定义需求 | 定义系统行为 | 沟通和排优先级 |
| 抽象层级 | 高层（what & why） | 低层（how） | 中层（what） |

Cooper 的核心立场：**先有场景（理解需求），再有用例（定义系统），用户故事是沟通工具而非需求定义工具。**

**论点 3：设计需求不是功能列表**

"需求"在行业中常被滥用为一个功能清单。Cooper 重新定义了需求：
- 数据需求 = 用户需要看到和操作的对象
- 功能需求 = 用户需要在这些对象上执行的操作
- 情境需求 = 对象之间的关系和依赖

设计需求描述的是用户的"What"（需要什么），而不是解决方案的"How"（通过什么功能实现）。

**论点 4："假装它是魔法"是突破思维定式的关键**

在早期场景中，假设界面是"魔法"的——Persona 只要能想到，产品就能做到。这使设计团队能够：
1. 不受现有技术限制地想象理想用户体验
2. 发现用户的真实需求而非被已有功能框定
3. 在理想与现实之间找到最佳的折中点

### 四、方法论与工具

**三种场景类型及其在整个设计流程中的位置**：

| 场景类型 | 所处阶段 | 关注重点 | 输入 | 输出 |
|----------|----------|----------|------|------|
| 情境场景 | 需求定义 | 理想用户体验 | Persona + 目标 | 设计需求 |
| 关键路径场景 | 框架定义 | 主要交互路径 | 设计需求 + 框架 | 交互框架优化 |
| 验证场景 | 细化 | 边缘情况压力测试 | 关键路径场景 | 设计修正 |

**需求定义的完整流程**：

1. **创建问题声明和愿景声明**：设计团队的行动纲领
2. **探索与头脑风暴**：基于研究数据进行发散思维
3. **识别 Persona 期望**：基于其心智模型预设产品行为
4. **构建情境场景**：以 Persona 为主角的理想体验叙事
5. **提取设计需求**：从场景中分析出数据/功能/情境需求

**"假装它是魔法"的操作方法**：

- 写场景时，用"Persona 可以直接想到..."而非"Persona 点击按钮..."
- 第一次迭代完全忽略技术可行性
- 完成后逐一评估哪些"魔法"通过合理设计可以接近实现

**一个完整情境场景的结构**：

```
1. 设定（Setting）：时间、地点、情境
2. 触发器（Trigger）：什么事件触发了这次使用
3. 行动（Actions）：Persona 如何与产品互动
4. 结果（Outcome）：Persona 达成了什么目标
5. 感受（Feeling）：Persona 在过程中和结束后的情绪状态
```

### 五、案例与实践应用

**PDA 电话情境场景示例**：

本章包含一个完整的 PDA 型手机的情境场景。关键特点：
- 以具体的 Persona（Vivien）为主角
- 描述她在机场使用手机的场景
- 不提及任何具体的界面元素（按钮、菜单等）
- 聚焦于她的目标（了解航班延误、重新安排行程）和感受（不被打扰、保持掌控）

从这个场景中可以提取出数十条具体的设计需求（如"系统应能在航班变化时主动通知用户"），然后这些需求在 CH 5 中被转化为具体的界面设计。

### 七、学术评价与反思

**优点**：

- 场景方法使设计决策可以在"不画界面"的阶段就进行高层决策
- "假装它是魔法"是一种有效的创造性约束解除技术
- 将需求定义为"用户需要什么"而非"产品应该有什么功能"是一种认知框架的升级
- 三种场景类型的区分解决了不同设计阶段的不同信息需求

**局限**：

- 情境场景的写作质量高度依赖作者的同理心和叙事能力，标准化程度低
- 从场景到需求的"提取"过程在书中描述较模糊，初学者可能难以操作
- 在敏捷开发环境中，详细的情境场景可能被认为"过于重量级"
- 场景方法对"现有产品的渐进式改进"场景的适用性弱于"全新产品设计"
